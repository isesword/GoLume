# Directional fill validation

2026-11-07, Go 1.27.3, linux/amd64, AMD EPYC 9V74 shared host.

Production implements numeric `ForwardFill`/`BackwardFill` in explicit ordered
windows. Native scalar cells preserve all ten widths, NULL versus NaN, partition
boundaries and stable equal-key order. Backward lookahead uses admitted owned
batches, a monotone per-expression search cursor and explicit memory-budget
failure for runs that cannot fit; it neither assumes replay nor silently spills.

`tests.txt` records full physical/logical/expr package tests (logical regression
added afterward separately), focused SIMD and SIMD race tests, and GoDoc.
`integration.txt` records focused logical/physical/lazy tests and pinned Polars
fixture verification in the isolated fills snapshot. The earlier live-tree lazy
rerun hit unrelated in-progress endpoint code; that is not a fill failure or a
claimed full live-tree pass. Parent owns the final isolated full-package gates.

New tests include every numeric width with batch sizes 1/3/64; UInt64 maximum;
NaN propagation; empty/all-NULL inputs; alias replacement and private-name
collision; mixed past/future Shift and fills; resident/ordered/external execution;
stable ties/original-row restoration; explicit unsupported-type/frame checks;
budget, cancellation, child failure, early-close and idempotent-close cleanup.
Forty pinned Polars 1.35.2 observations are generated by
`scripts/fills_polars_oracle.py` and consumed directly by Go tests.

## Long NULL-run baseline

Command: `GOMAXPROCS=1 go test ./physical -run '^$' -bench
'^BenchmarkDirectionalFillLongNullRun$' -benchmem -benchtime=300ms -count=3`.
Each input ends with its only valid value. Stream batch size is 128; construction
is outside timing, stream open/consume/close inside. Enum 11 is ForwardFill and
12 is BackwardFill in the raw benchmark log.

- Forward, 4,096 rows: median 0.989 ms; 57,712 B/op, 256 allocations.
- Backward, 4,096 rows: median 1.679 ms; about 202,970 B/op, 1,186 allocations.
- Forward, 65,536 rows: median 13.393 ms; 660,592 B/op, 3,136 allocations.
- Backward, 65,536 rows: median 31.401 ms; about 2,941,059 B/op, 17,508 allocations.

Sixteen times more rows produced roughly 18.7 times the backward execution time
on this shared host, consistent with the amortized linear algorithm rather than
quadratic repeated NULL-run scans. This is a baseline, not a regression gate or
SIMD speedup claim. Bytes/op are total allocations, not peak retained memory.
No new SIMD kernel is enabled without measured architectural evidence.
